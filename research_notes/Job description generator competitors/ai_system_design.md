# AI / System Design Best Practices for an LLM Job Description Generator (near-zero budget)

Scope note: ~12 searches/fetches done. Most sources are secondary (blogs, vendor posts); official pages fetched directly: OpenAI structured outputs, Cloudflare Turnstile plans. Items not verified against primary sources are flagged. Current date context: Nov 2026.

## Q1. Which system-design improvements give the biggest recruiter-visible quality gain?

### Takeaway
Highest visible value per effort: (1) reliable structured output with explicit refusal/truncation/retry handling, (2) a rule-based quality + inclusivity + pay-compliance "linter" shown in the UI, (3) atomic idempotent credit ledger and webhook dedup, (4) a public eval dashboard and architecture page. All are low-cost and demonstrable. No source directly measured "recruiter-visible" impact; ranking is my inference from what hiring-facing portfolios can show.

### Cited Findings
- Structured Outputs constrains non-refusal output to the JSON schema; older JSON mode only guarantees valid JSON. A refusal may not follow the schema (check `refusal` field); output can be cut off at max tokens (check status/incomplete); app must still validate business rules the schema cannot express. — [OpenAI Structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs.md)
- First request with a new schema is slower (schema processed); later requests are not. Use clear key names, titles and descriptions, and evals to pick best structure. — [OpenAI Structured outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs.md)
- Third-party reports: valid JSON can still be semantically wrong; a 2026 vendor piece reports occasional strict-mode parse failures, so validation and retry remain necessary; a forum thread questions whether strict always enforces schema (unverified). — [FutureAGI 2026 structured-output evaluation](https://futureagi.com/blog/evaluating-llm-structured-output-modes-2026/); [OpenAI forum thread](https://community.openai.com/t/strict-mode-does-not-enforce-the-json-schema/1104630.md); [BenchLM "Valid JSON can still be wrong"](https://benchlm.ai/md/blog/posts/test-structured-output.md)
- Strict schemas need `additionalProperties: false` and all fields listed in `required` (secondary source). — [OpenReplay](https://blog.openreplay.com/json-schema-llm-structured-outputs/)
- LLM-as-judge: use pairwise with position swap (count win only if it holds in both orders) for release gates, pointwise for monitoring; use criterion-specific rubrics and binary/1-5 scales; cross-check judge with a different provider and sample human labels. — [Cameron Wolfe overview](https://cameronrwolfe.substack.com/p/llm-as-a-judge); [Grepture on judge bias](https://grepture.com/blog/llm-as-a-judge-bias)
- Langfuse Hobby (free): reported 50,000 units/month, 30-day data, 2 users; paid Core $29/mo. Third-party sites vary; check live page. — [Langfuse pricing](https://langfuse.com/pricing)
- Textio (vendor, not independent) tested 167 ChatGPT-written job posts and reported bias even in generic posts, with race and age bias more common than gender bias, and more specific prompts producing more biased posts. — [Textio blog](https://primary.textio.com/blog/chatgpt-writes-job-posts)
- A single informal review says ChatGPT-written JDs are longer/faster but need significant editing for bias and clarity versus Textio. — [index.dev Textio review](https://www.index.dev/blog/textio-review)

### Inferences
- Showing a "quality report" (inclusivity score, pay-transparency check, specificity score, schema pass) beside each JD is the most visible differentiator versus generic ChatGPT output, and the Textio finding gives a pitch: "specific prompts can increase bias, so we lint output".
- Showcase ideas (no sources, my suggestions, all near-zero cost): public `/eval` page generated from the existing eval harness (per-model quality + cost per JD, run date, dataset size); `/architecture` page with sequence diagram of intake state machine -> generate -> validate -> lint -> render; open-source the eval set and rule linter as a small pip package; a changelog of eval score per prompt version; Langfuse public trace screenshots (redacted).

### Gaps
- No source quantifying recruiter reaction to specific portfolio features.
- No primary source on streaming structured JSON in FastAPI (SSE) was fetched; general approach: stream raw markdown text for perceived speed, or stream JSON deltas and validate on completion. Not verified.
- Helicone and OpenRouter observability free-tier details not researched (out of search budget).

## Q2. Common failure modes of an anonymous free endpoint and cheap fixes

### Takeaway
Main risks: shared-IP rate limiting behind HF's proxy (everyone looks like one IP, or headers are spoofable), bot abuse draining LLM spend, credit double-spend/race conditions, duplicate Stripe webhooks, and prompt injection via uploads. Cheap fixes: Cloudflare Turnstile (free), trusted-proxy IP handling, per-IP + global daily budget cap, atomic Postgres RPC with unique idempotency key, event-ID dedup table.

### Cited Findings
- Turnstile free plan: up to 20 widgets, 10 hostnames/widget, "unlimited challenges", all widget types, 7-day analytics. — [Cloudflare Turnstile plans](https://developers.cloudflare.com/turnstile/plans)
- Conflict: Cloudflare's GA blog is cited as mentioning a 1 million siteverify limit for advanced features; the plans page fetched shows no such limit. — [Cloudflare blog](https://blog.cloudflare.com/turnstile-ga/); [Piano docs](https://docs.piano.io/en/subscriptions/cloudflare-turnstile)
- Server validation is a POST to `https://challenges.cloudflare.com/turnstile/v0/siteverify` with secret + token; check `success`; secret stays server-side; optional `remoteip`. Token single-use, ~300 s expiry (secondary source, unverified). — [Splitforms guide](https://splitforms.com/blog/cloudflare-turnstile-html-form); [Issoh guide](https://www.issoh.co.jp/column/details/3443)
- slowapi keys on client IP by default; if proxy headers are not configured, all users share the proxy IP. Reading raw `X-Forwarded-For` is spoofable; trust headers only from the proxy. — [Litestar XFF spoofing advisory (analogous)](https://corgea.com/advisories/vulnerabilities/CVE-2025-59152); [FastAPI proxy security guide](https://rennf93.github.io/fastapi-guard/latest/tutorial/security/proxy-security)
- Atomic credits pattern: Postgres function called via Supabase `rpc()` runs in one transaction; conditional single UPDATE ... WHERE balance >= cost RETURNING; append-only ledger with unique `idempotency_key` for every spend/grant/refund so retries roll back. Reservation then settle/refund on failure. — [DEV: credit system Stripe+Supabase](https://dev.to/youngalgy/how-to-build-a-credit-system-for-a-nextjs-ai-app-stripe-supabase-heb); [DEV: credit ledger](https://dev.to/ritusmoikaushik/metering-a-paid-api-without-overselling-the-credit-ledger-behind-a-solo-saas-3jej); [Reservation flow](https://instagit.com/freestylefly/awesome-gpt-image-2/how-reservation-based-generation-flow-prevents-credit-loss.md)
- Stripe webhooks are at-least-once; retries reported up to 72 h; store processed event IDs with unique constraint (`INSERT ... ON CONFLICT DO NOTHING`), return 200 on duplicates, keep dedup records at least the retry window, test with `stripe events resend`. Stripe API idempotency keys (24 h) are a different thing from webhook dedup. — [Activepieces](https://www.activepieces.com/blog/webhook-idempotency-how-to-handle-duplicate-events-2026); [DEV: Stripe webhook idempotency in FastAPI](https://dev.to/uaslimcreate/stripe-webhook-idempotency-in-fastapi-handling-duplicate-events-without-double-charging-saas-5gbe); [Hookdeck](https://hookdeck.com/webhooks/guides/webhook-delivery-guarantees)
- Prompt injection: OWASP lists indirect injection via files (e.g. resume with split payloads); not fully preventable; treat uploaded docs as untrusted; layer controls; limit model permissions; filters are bypassable. — [OWASP LLM01 (via secondary summaries)](https://llmarmor-website.pages.dev/blog/owasp-llm01-prompt-injection/); primary: https://genai.owasp.org/llmrisk/llm01-prompt-injection/ (not fetched)
- HF Spaces: CPU Basic is 2 vCPU, 16 GB RAM, 50 GB disk, free; sleeps after 48 h inactivity; wakes on visit; free sleep time not configurable. — [HF Hub Spaces overview](https://huggingface.co/docs/hub/en/spaces-overview); [huggingface_hub space_runtime](https://huggingface.co/docs/huggingface_hub/en/package_reference/space_runtime.md)
- Unofficial/conflicting: a forum post claims free CPU Basic and Docker SDK were restricted for unpaid accounts; official docs still list free CPU Basic. Verify. — [HF forum complaint](https://discuss.huggingface.co/t/official-community-complaint-revert-free-cpu-basic-spaces-and-remove-anti-developer-sdk-restrictions/177703)
- Prompt caching (OpenAI): automatic for prompts >=1024 tokens, exact prefix match, 128-token increments; discount differs by source/model (50% at launch; newer models may differ and some bill cache writes at 1.25x). — [OpenAI prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); [OpenRouter prompt caching](https://openrouter.ai/docs/prompt-caching)

### Inferences
- Cheap defense stack for anonymous endpoint: Turnstile token required per generation -> per-IP and per-fingerprint daily limit -> global daily spend cap (kill switch returning "try later") -> max_tokens + input length caps -> lower-cost model for anon tier (optional).
- Test the real client IP seen on HF by sending a forged `X-Forwarded-For` to the deployed Space; HF specifics not found in sources.
- Put static instructions/schema first in prompt, variable user data last, to benefit from automatic caching; response cache keyed on hash of normalized intake answers for repeat/demo requests.
- For uploads: extract text, cap size, strip to plain text, wrap in delimiters with "data only" instruction, use extractor model with strict schema (no tools), then validate output fields by length/type; never let uploaded text reach a prompt that has secrets or tools. Mention injection test cases in the public eval set.
- HF cold start: use a lightweight `/health` endpoint, uptime pinger (free external cron) to avoid sleep, loading-state UI. Background jobs: FastAPI BackgroundTasks or asyncio for post-generation logging; for refund-on-failure, use try/finally plus a periodic sweeper that refunds stale "reserved" ledger rows.
- Cost per JD (my estimate, not sourced): a JD is roughly 2-3k input and 1-2k output tokens; at gpt-4o-class list pricing (verify current price) this is on the order of a few US cents per JD; the eval harness already tracks cost and should publish the real number.

## Q3. What quality checks can be done with no extra LLM cost (rule-based)?

### Takeaway
A deterministic linter can cover gender-coded words, age-coded phrases, pay-range presence/validity, required sections, length and readability, schema validity, and boilerplate/generic phrase detection. Research gives word lists and legal context; thresholds are for the builder to tune.

### Cited Findings
- Gaucher, Friesen and Kay (2011, JPSP 101(1), 109-128; doi 10.1037/a0022530) analyzed 4,000+ job ads; masculine-coded wording made roles less appealing to women and sustained inequality; examples masculine "competitive", "dominant"; feminine "compassionate", "nurturing", "support", "understand", "interpersonal". Full word lists are in the paper (not retrieved). — [Duke Fuqua summary](https://www.fuqua.duke.edu/duke-fuqua-insights/employment-ad-gender-roles); [Heriot-Watt PDF](https://www.hw.ac.uk/uk/services/docs/gendered-wording-in-job-ads.pdf); [Univ. of Oregon gender decoder PDF](https://provost.uoregon.edu/files/gender_decoder_final.pdf)
- SHRM (via Textio data): "sympathetic", "caring", "empathetic", "families" appeal more to women; "manage", "proven", "superior" more to men. — [SHRM](https://www.shrm.org/ResourcesAndTools/hr-topics/technology/Pages/Do-Your-Words-Deter-Women.aspx)
- Ageism: UCI-led NBER study found three subtle ageist phrase categories (communication, physical, tech skills) cut over-40 applicants by 12 percentage points; "recent graduate" reduced likelihood to apply; "digital native" flagged by AARP; US guidance warns against "recent college graduate". — [UCI](https://www.socsci.uci.edu/newsevents/news/2022/2022-08-04-ageist-language-in-job-ads-discourages-older-applicants-uci-led-study-finds.php); [Centre for Ageing Better](https://ageing-better.org.uk/sites/default/files/2021-04/understanding-recruitment-language-GROW.pdf); [AARP](https://www.aarp.org/work/age-discrimination/age-bias-language-job-listings)
- Pay transparency (US): Colorado first broad statewide law (2021); California requires range for employers with 15+ employees, applies to postings that could be filled in CA incl. remote; Washington good-faith pay scale from Jan 1 2026; Virginia and Maine effective July 2026; NYC under Admin Code 8-107(32). Penalty figures conflict between secondary sources; verify statutes (Cal. Lab. Code 432.3, C.R.S. 8-5-201). — [Cooley July 2026](https://www.cooley.com/news/insight/2026/2026-07-06-show-me-the-money-or-the-wage-range-new-state-pay-transparency-laws); [Foley June 2026](https://www.foley.com/insights/publications/2026/06/3-new-pay-transparency-state-laws-raise-compliance-risks/); [Bloomberg Law](https://news.bloomberglaw.com/us-law-week/pay-attention-to-state-pay-transparency-laws-when-posting-jobs); [Clockspot](https://www.clockspot.com/research/pay-transparency-laws-by-state)
- EU Pay Transparency Directive: transposition deadline 7 June 2026 (passed); employers must give starting pay or range in the advert or before the first interview (member states differ; Ireland and a Dutch draft require it in the advert); ranges must reflect actual pay (artificially wide ranges not acceptable); transposition status varies by country. Sources are HR vendor blogs, no EUR-Lex text read. — [Assessio country tracker](https://assessio.com/articles/pay-transparency-directive-country-tracker/); [Figures HR](https://figures.hr/post/eu-transparency-job-ads); [DEV: tech hiring after June 7 2026](https://dev.to/julien786534/eu-pay-transparency-directive-what-changes-for-tech-hiring-after-june-7-2026-210j)

### Inferences
- Rule checks (zero LLM cost): (a) gender-coded word count from Gaucher lists, flag imbalance; (b) age-coded phrase regex (digital native, recent graduate, young and energetic, high energy, X years max); (c) credential inflation: degree required + no "or equivalent experience", years-of-experience higher than tech age (e.g. 10 years for a technology that is younger), entry-level title with 3+ years; (d) pay block present with min<=max, currency, period, and narrow-range ratio (e.g. max/min <= ~1.5, threshold is a suggestion); (e) jurisdiction toggle (NYC, CA, CO, WA, EU) that makes pay fields required; (f) required sections present, bullet count caps (e.g. 5-8 requirements), must-have vs nice-to-have split; (g) generic filler list ("rockstar", "ninja", "fast-paced environment", "team player", "passionate"); (h) reading level (Flesch) and length; (i) hallucination guard: every skill/requirement in output must trace to user intake answers or be marked "suggested"; (j) EEO statement present; (k) deduplicate requirements.
- Degree inflation: no research source was found in this pass; treat (c) as a heuristic.
