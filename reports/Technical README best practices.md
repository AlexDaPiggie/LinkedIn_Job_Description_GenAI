# Rebuild the README around evidence, not adjectives

The best-documented products treat the README as a short landing page: one plain sentence saying what the product is, a screenshot or live link, a few features each tied to a mechanism, a brief "how it works" with one diagram, a run-it-locally block, and links out to deeper docs. Every claim has a receipt - a number with its setup, a chart with its method, a test command, a CI badge. Our README does the opposite in its top half: clickbait headings, an authors table before any description, unprovable superlatives ("better than most free-tier AI models", "guarantees"), typos, and facts that are wrong (provider list, env var names, latency). The two most damaging problems are checkable in under a minute: the "< 2 s latency" claim is contradicted by our own CSV (2.87 s mean for gemini-2.5-flash-lite, 5.32 s for gpt-4o-mini), and the setup section lists API keys the code never reads, so a reader following it cannot run the app. The good news is that the substance is strong and undersold: real cost/token and latency charts over 22 models, a reproducible eval harness, an atomic credit ledger with idempotent Stripe webhooks, 74 offline tests that pass in under 3 seconds, and honest limits already written on eval.html. The fix is mostly editorial: keep the charts and add their method, cut the marketing, correct the facts, surface tests and design decisions, and move reference material (env vars, deploy steps, eval details) into separate docs.

## Praised READMEs are short landing pages that route to deeper docs

Product READMEs with a docs site are short. Next.js's package README is **50 lines / 291 words** and links almost everything to nextjs.org ([Next.js](https://github.com/vercel/next.js/blob/canary/packages/next/README.md)); Plausible is 143 lines, Immich 128, Supabase 288 ([Plausible](https://github.com/plausible/analytics), [Immich](https://github.com/immich-app/immich), [Supabase](https://github.com/supabase/supabase)). The long ones get long from reference material, not prose: Cal.com reaches **837 lines** mostly through six hosting targets and about twelve per-provider OAuth credential walkthroughs ([Cal.com](https://github.com/calcom/cal.com)). That is the content guides say to move out. Make a README advises moving material to a docs site when the README gets unwieldy rather than deleting it ([Make a README](https://www.makeareadme.com/)), and Diataxis argues that mixing tutorial, how-to, reference and explanation in one place is at the heart of many documentation problems ([Diataxis](https://diataxis.fr/start-here/)).

The opening screen follows a pattern. Products define themselves in one plain sentence: "Supabase is the Postgres development platform", "Plausible Analytics is an open source, privacy-first web analytics tool" ([Supabase](https://github.com/supabase/supabase), [Plausible](https://github.com/plausible/analytics)). Plausible follows that with five short linked bullets and a dashboard screenshot; Ollama goes straight to a copy-paste install command per OS ([Ollama](https://github.com/ollama/ollama)). Stripe's SDKs use the most neutral register of all - the library "provides convenient access to the Stripe API" - with no quality adjectives and with scope limits stated up front ([stripe-node](https://github.com/stripe/stripe-node)). Art of README calls this "cognitive funneling": broad and most pertinent first, details later, so the reader can decide quickly whether to keep going ([Art of README](https://benbridle.com/art-of-readme.html)).

Architecture appears once, briefly. Supabase's README has a single "How it works" section: one diagram and one sentence per component ([Supabase](https://github.com/supabase/supabase)). Its architecture page adds principles that explain choices such as Postgres over NoSQL ([Supabase Architecture](https://supabase.com/docs/guides/getting-started/architecture)). Stack sections sit near the end and stay short (Twenty "Stack", Plausible "Technology") ([Twenty](https://github.com/twentyhq/twenty), [Plausible](https://github.com/plausible/analytics)). Plausible's "Why" bullets pair each benefit with a mechanism - no personal data or IP addresses stored, no cookies - instead of a superiority claim ([Plausible](https://github.com/plausible/analytics)). "We" is used for intent and decisions, not praise ([Infisical](https://github.com/Infisical/infisical), [Supabase](https://github.com/supabase/supabase)).

Google's developer style guide gives the tone rules: friendly and respectful, no buzzwords, no exclamation marks, no "simply", "easy" or "quickly" in procedures, no long-winded or choppy sentences ([Google style guide](https://developers.google.com/style/tone)). Practitioners name the tells of AI-drafted READMEs: emoji bullets, stock header images, generic openers ([DEV Community](https://dev.to/eschmechel/your-ai-slop-bores-me-4g7k)), heavy em-dash use ([NCC Group](https://www.nccgroup.com/media/l5cjcey2/unmasking_techno_sophists.pdf)), build-status chatter instead of what the reader can do, development history mixed into user docs, and over-documented internals - with the limitations section singled out as the part worth keeping ([HackerNoon](https://hackernoon.com/treat-ai-generated-readmes-like-first-drafts)). Some praised repos do use emoji and badge walls (Langfuse, Dify, Excalidraw), but they have a live product and real adoption underneath; a portfolio README has no such cushion, so the plain Stripe and Next.js register is the safer model.

Hiring-side advice is thinner and mostly opinion, but it converges: write for developers while knowing a hiring manager is reading, show screenshots and a demo, explain architecture, and do not just upload code ([HackerNoon, hiring manager FAQ](https://hackernoon.com/faqs-for-a-software-engineering-hiring-manager-part-3-of-5-portfolios-and-githubs)); a README without install steps is a project nobody will try ([Underdog.io](https://underdog.io/blog/what-hiring-managers-look-for-on-github)). Where a portfolio README should diverge from a product README is a short "design decisions" section and a "limitations" section - product READMEs serve users, but a reviewer wants to see judgment.

What we can apply directly:

| Practice | Who does it well | How to apply here |
|---|---|---|
| One-sentence "X is a Y for Z" opener | Supabase, Plausible, FastAPI | "Generates LinkedIn job postings from a short role brief, with a refine loop and Word export." |
| Screenshot or demo right after the pitch | Plausible, Immich | Use `front_end/images/social-preview.png` or a fresh GIF of generate then refine. |
| Features as one line each, with a mechanism | Plausible, PostHog, Supabase | "Output validated against a Pydantic schema; retried once on bad JSON." |
| One diagram plus one line per component | Supabase | Browser -> FastAPI -> Supabase / Stripe / OpenRouter / Turnstile, as Mermaid. |
| Neutral tone, no adjectives without receipts | Stripe SDKs, Google style guide | Every "fast" or "cheap" becomes a number with a link to its method. |
| README as router to deeper docs | Next.js, Immich, Langfuse | Env vars, deploy, evals, decisions each get their own file. |
| Short stack section near the end | Twenty, Plausible | One table: layer, tool, why. |
| Honest limitations | ClickBench, our own eval.html | Small n, one network location, AI judge bias, in-memory rate limits. |

## Credible numbers carry their model, setup, sample size and date

Model makers that are trusted attach settings to every number. OpenAI's simple-evals table lists the system prompt used per model, pins dated snapshots, footnotes deviations and flags saturated benchmarks; it also carries a banner saying it is no longer updated for new models ([simple-evals](https://github.com/openai/simple-evals)). Anthropic's Opus 4.5 post states thinking budget, context size and that results were **averaged over 5 independent trials**, and it discloses flattering factors such as best-of-N runs and competitor re-runs ([Anthropic](https://www.anthropic.com/news/claude-opus-4-5)). Anthropic's eval-statistics guidance asks for a standard error with every score and paired comparisons between models ([Anthropic research](https://www.anthropic.com/research/statistical-approach-to-model-evals)). Chatbot Arena shows the vote count per model and says plainly that fewer votes mean wider confidence intervals ([LMSYS](https://lmsys.org/blog/2023-12-07-leaderboard/)).

Cost and latency need definitions. Artificial Analysis separates time to first token, end-to-end time and output speed, uses a stated rolling window, defines which errors count, and states its price blend ratio ([Artificial Analysis](https://artificialanalysis.ai/methodology)). LiteLLM's benchmark page reports **p50/p95/p99** latency with the full setup (pods, vCPU, RAM, load tool, users, request rate) and labels that a mock backend excludes provider latency ([LiteLLM](https://docs.litellm.ai/docs/benchmarks)). ClickBench stores results in dated, machine-tied files, records failures as null instead of dropping them, labels tuned configs separately, and ends with a frank limitations list ([ClickBench](https://github.com/ClickHouse/ClickBench)).

In software READMEs the strongest pattern is one headline chart plus a link to a methodology doc. uv's BENCHMARKS.md gives the real project used, four scenarios (warm and cold install and resolve), the exact repro and chart-render commands, and caveats about OS and filesystem ([uv](https://github.com/astral-sh/uv/blob/main/BENCHMARKS.md)). Ruff shows a chart with a workload caption but no methodology link, which is the weaker version ([Ruff](https://github.com/astral-sh/ruff)). FastAPI's speed claims are footnoted and linked to a Performance section rather than asserted ([FastAPI](https://github.com/fastapi/fastapi)).

LLM-as-judge results need extra care. Hamel Husain recommends binary pass/fail with a written critique over 1-5 scales, and validating the judge against human labels with true- and false-positive rates reported separately ([Hamel Husain](https://hamel.dev/blog/posts/llm-judge/)). Eugene Yan documents judge biases: verbosity (longer answers preferred over 90% of the time even with no added information), self-preference (gpt-4 about +10%), and score inflation; he also shows raw agreement can hide weak agreement (80% raw but kappa 0.62) ([Eugene Yan](https://eugeneyan.com/writing/llm-evaluators/)). promptfoo shows what a credible judge config looks like: rubric text, pinned grader model and temperature, and a pass threshold ([promptfoo](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/llm-rubric/)). For structured output, JSONSchemaBench separates schema coverage from compliance and counts timeouts as failures ([JSONSchemaBench](https://arxiv.org/html/2501.10868v3)).

For this project, that means the owner's two favorite charts can stay as the visual centerpiece - they are generated from real API token usage and real wall-clock timing, which is exactly what makes them credible. What they lack is the caption and method: 22 models, 4 scenarios x generate + refine, 1 run each, run Aug-Sep 2026 via OpenRouter from one client location, which models use real prices and which use a placeholder, and the judge model. Pair each chart with a small markdown table of exact values (images alone cannot be inspected), and write "8/8" instead of "100%".

## Verification and deployment are shown with commands, badges and invariants

Credible repos show verification as runnable commands and one CI badge, not prose. GitHub's workflow badge is a single URL per workflow ([GitHub Docs](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)). Cal.com's README gives the exact e2e command, how to view the report, and the env needed ([Cal.com](https://raw.githubusercontent.com/calcom/cal.com/main/README.md)). For LLM products, evals in CI are now a known signal: the promptfoo GitHub Action runs evals on PRs that touch prompts, with a pass threshold and a repeat option for nondeterminism ([promptfoo-action](https://github.com/promptfoo/promptfoo-action)). Popularity badges (stars, downloads, Discord) dominate Langfuse's and Cal.com's READMEs ([Langfuse](https://raw.githubusercontent.com/langfuse/langfuse/main/README.md)), but on a two-person portfolio repo they look hollow; a test badge and a license badge are enough.

Architecture docs that engineers respect are short and stable. matklad's ARCHITECTURE.md guidance: bird's-eye view, a codemap ("where does the code for X live"), invariants - especially ones expressed as an absence - and cross-cutting concerns; name files but do not link them, and record only facts unlikely to change ([matklad](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)). rust-analyzer's version uses about two dozen bold "Architecture Invariant" callouts ([rust-analyzer](https://raw.githubusercontent.com/rust-lang/rust-analyzer/master/docs/book/src/contributing/architecture.md)). Immich pairs one diagram with one-line service responsibilities and data flow ([Immich](https://docs.immich.app/developer/architecture)). GitHub renders Mermaid natively, so a diagram can live as diffable text ([GitHub Docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)).

Deployment and config live outside the README. Langfuse keeps deploy options to a short list and puts its roughly 110 env vars in three-column tables (Variable | Required/Default | Description) on a separate page ([Langfuse config](https://langfuse.com/self-hosting/configuration)). Plausible CE covers four env vars in the README and defers the rest to its wiki ([Plausible CE](https://github.com/plausible/community-edition)). Cal.com splits dev and prod migration commands, a cheap credibility signal ([Cal.com](https://raw.githubusercontent.com/calcom/cal.com/main/README.md)). Decisions go in short ADRs: MADR uses numbered files in `docs/decisions` with context, considered options and outcome ([MADR](https://adr.github.io/madr/)), and PostHog shows that rejected options backed by numbers (EFS at about $600/day actual vs a $300/month estimate) are what impress ([PostHog](https://posthog.com/newsletter/choosing-technologies)).

For a payments product, Stripe's own docs are the checklist a reviewer will compare against: verify the signature on the raw body, dedupe by event ID, do not rely on event order, return 2xx fast, expect retries for up to three days ([Stripe webhooks](https://docs.stripe.com/webhooks)). Our ledger and webhook code already covers the dedupe part (`spend_credits`, `claim_stripe_event`, 40 billing tests), so a "risk -> mechanism -> test" table turns existing work into visible evidence.

## Conclusion

The gap between this project and a well-documented product is not engineering - the ledger, harness, tests and linter already exist - but trust. A technical reader decides within the first screen whether to believe the rest, and right now the README spends that screen on clickbait, bios and a superlative, then loses the reader for good at a latency number the repo itself refutes. Products like Stripe, Supabase and Plausible earn trust by saying less and proving more; for a portfolio, that discipline is itself the skill being shown. The charts the owner likes are the right centerpiece, because they come from real measurements - they only need captions, real prices and an honest method note to go from "nice picture" to "this person knows how to evaluate LLMs".

One uncertainty matters for ordering the work. The eval itself has method problems (placeholder prices, a self-preferring judge, single runs, possible fallback contamination), so polishing the README before fixing the harness risks documenting numbers that will change. The efficient order is: fix the wrong facts and remove the marketing (an hour); make live tests opt-in and add CI (an hour); fix the pricing table and fallback labeling, re-run the benchmark with a timestamp column, and redraw the two charts; then write EVALS.md and the README model-choice section from the fresh data. External links (live site, video) were not checked in this audit and should be verified before publishing.
